# 人物专访深度报道・多智能体编排 SOP v9

> 更新：2026-11-06。**v9 不修改 v8 的任何内容规则**，只在它外面加一层"谁来做、什么时候做、做完谁验收"。
> v8 管「写得对不对」，v9 管「能不能无人值守地跑、跑歪了谁拦住」。
> 入口：`人物专访深度报道_标准工作流SOP_v8.md`（内容规则）→ 本文（编排规则）。两者冲突时，**内容判据以 v8 为准，编排判据以 v9 为准**。

---

## 01｜为什么扩展

v8 是一条**单线程的人工流程**：一个人依次做选题、转写、台账、研究、写作、体检、排版、验收。它的问题不在质量，而在三点：

| 问题 | 表现 | v9 的解法 |
|---|---|---|
| 串行 | 一篇稿子从素材到交付 60—90 分钟，全占一个人的注意力 | 阶段并行、断点续跑：状态外置到磁盘，任何时候中断都能从那一步继续 |
| 无守夜 | 新素材出现时没人知道，隔几天才处理 | 事件循环：定时扫描源列表 + inbox 投递，自动建任务 |
| 判据在人脑 | "观点体检""删稿验收"靠自觉，跳过了没人发现 | 把 v8 的可判定规则写成门禁，不通过就卡住，不能靠"我觉得可以"放行 |

一句话：**v9 把 v8 的检查清单变成机器能执行的闸门，把人的注意力只留在两处——选题定调和发布拍板。**

## 02｜总体架构

```
        ┌────────────── 事件源（触发层） ──────────────┐
        │  ① cron 扫描 sources.json（RSS / YouTube）    │
        │  ② inbox/ 手动投递（链接 / 音频 / 逐字稿）      │
        │  ③ CLI 新建（人肉补单）                        │
        └───────────────────┬──────────────────────────┘
                            ↓  去重（内容哈希 = run_id）
        ┌───────────────────▼──────────────────────────┐
        │              编排器 loop.py（一个 tick）        │
        │   取事件 → 建/续 run → 推到下一个闸门 → 落盘     │
        └───────────────────┬──────────────────────────┘
                            ↓
   ┌────────────────────────▼─────────────────────────────────┐
   │  阶段（stage）＝ 一个智能体 ＋ 一份产物 ＋ 一组验收判据        │
   │                                                          │
   │  scout → transcriber → ledger → researcher → writer      │
   │        → critic → composer → gatekeeper → archivist      │
   │           ↑           │                                  │
   │           └─ rework ──┘   （打回，带具体原因）              │
   └────────────────────────┬─────────────────────────────────┘
                            ↓
        ┌───────────────────▼──────────────────────────┐
        │  产物：案例目录 NN_XX_案例/（md / html / png）  │
        │  状态：orchestrator/runs/{run_id}/state.json   │
        │  人工闸门：选题确认、发布确认（停在 awaiting_*）  │
        └──────────────────────────────────────────────┘
```

**核心设计取舍**：编排器本身**不含任何内容判断**。它只做三件事：调度、持久化、拦闸门。所有"写得怎么样"的判断都在 agent 内，且必须能对应到 v8 的某一条。

## 03｜九类智能体与职责边界

每个智能体对应 v8 的一到两节，产物是**文件**，不是聊天记录。

| # | 智能体 | 对应 v8 | 输入 | 输出（文件） | 完成判据 |
|---|---|---|---|---|---|
| 1 | `scout` 选题侦察 | §02 | 素材链接/标题 | `选题卡_YYYY-MM-DD_嘉宾.md` | 五项填满；「初步判断」是一句可复述的话，不是"技术变化很快" |
| 2 | `transcriber` 转写与素材卡 | §03 | 音频/视频/文稿 | `转写/transcript.json`、`素材卡_*.md` | 每段有时间戳；说话者不混；姓名/术语/数字标"待回听" |
| 3 | `ledger` 台账 | §03 | 素材卡 | `事实台账_*.md` | 九列齐全；**关键人物字段查不到就空着**，不猜 |
| 4 | `researcher` 研究 | §04 | 台账 + 外部检索 | `研究笔记_*.md` | 覆盖阶段/证据/对照/不确定性/暂定判断 |
| 5 | `writer` 写稿 | §05 | 台账 + 研究 + 素材卡 | `*_人味版.md` | 章节 01/02 编号；主线一句可复述；最强材料不埋在末节 |
| 6 | `critic` 观点体检 | §05 | 正文 | `体检报告_*.md` | 四关逐节打分；「可复述」不过即打回 writer |
| 7 | `composer` 排版 | §07 | 正文 + 人物卡 | 双 HTML + 三档渲染 PNG | 调用 `gzh_pipeline.py`，不允许自己拼 HTML |
| 8 | `gatekeeper` 门禁 | §09 | 双 HTML + 质检报告 | `_质检报告.md` 判定 | 任一 FAIL → 打回 composer；全过 → `awaiting_publish` |
| 9 | `archivist` 复盘 | §10 | 发布稿 + 本地稿 | `发布差异_*.md` | 逐项记录采用/删除/换图及原因；产出规则回写建议 |

**边界纪律**（沿用 v8 §05 的"两轮分离"）：

- `composer` 只改版式，不许改文字；发现要改文字，必须打回 `writer`。
- `critic` 只提判据，不许直接改稿；它写的是报告，不是新版本。
- `archivist` 只记录差异，不许把旧本地稿改名成"发布存档"（v8 §09 明确禁止）。

## 04｜状态机

```
new
 └→ triaged            （scout 完成，等人工确认选题）
      └→ transcribed   （transcriber）
           └→ ledgered （ledger）
                └→ researched （researcher）
                     └→ drafted    （writer）
                          └→ critiqued （critic，通过）
                               └→ composed   （composer）
                                    └→ qc_passed （gatekeeper，自动门禁全过）
                                         └→ awaiting_publish （人工闸门：停在微信编辑器实测）
                                              └→ published
                                                   └→ archived （archivist）
```

**打回（rework）**不是新状态，而是带原因的边：

| 打回 | 触发者 | 回到 | 必须携带 |
|---|---|---|---|
| 选题不成立 | 人工 | `triaged` 前（丢弃或改角度） | 一句"缺什么" |
| 观点不过关 | `critic` | `drafted` | 哪一节、哪一关、缺什么材料 |
| 门禁 FAIL | `gatekeeper` | `composed` | 具体门禁项与命中片段 |
| 编辑器实测失败 | 人工 | `composed` | 丢失的样式与截图 |

**状态非法转移一律报错退出**，不允许"顺手往前推一步"。状态文件是唯一真相，`state.json` 不存在的 run 视为 `new`。

## 05｜事件源与幂等

| 源 | 触发方式 | 去重键 |
|---|---|---|
| `sources.json` 里的频道 | cron 拉取 RSS，取 N 天内新条目 | 条目 GUID / 视频 ID |
| `inbox/` 投递 | 人把 `.md`（一行链接 + 可选备注）丢进目录 | 链接规范化后的哈希 |
| CLI | `loop.py submit --url ...` | 同上 |

**幂等规则**：`run_id = sha1(规范化链接)[:12]`。同一链接重复投递只更新 `source.notes`，不新建 run。RSS 回看窗口内已建过的不再建。

**为什么用文件而不是数据库**：产物本身就在文件系统里；状态跟着产物走，`git log` 就是审计日志；Actions 里做缓存回写不需要额外服务。

## 06｜闸门：哪些机器判，哪些必须人判

这是 v9 最需要克制的地方。**能机器判的必须机器判，不能机器判的绝不假装能判。**

| 闸门 | 判定者 | 依据 | 不通过 |
|---|---|---|---|
| HTML 硬规则 8 项 | 机器 | `gzh_pipeline.py` HARD_GATES | 阻塞 |
| 禁用词高危 | 机器 | `FORBIDDEN_WORDS` | 阻塞 |
| 禁用语语境词 | 机器提词 + 人判 | `FORBIDDEN_CONTEXT` | 提示，不阻塞 |
| 三档渲染溢出/图片比例 | 机器 | headless Chrome | 阻塞 |
| 占位符/本地路径/空 alt | 机器 | 流水线 | 阻塞 |
| 引文可定位 | **人** | 台账时间戳 ↔ 原视频 | 阻塞发布 |
| 事实是否已核实 | **人** | 台账核验状态列 | 阻塞发布 |
| 选题值不值得做 | **人** | 选题卡 | 停在 `triaged` |
| 能不能发 | **人** | 编辑器实测 | 停在 `awaiting_publish` |

三条不可自动化的红线（v8 §01 原文）：
1. 不把二次整理包装成原创采访；
2. 不因工期降低核验门槛；
3. 未经编辑器保存与手机预览，不得标记"可发布"。

**机器的职责是让这三条更难被违反**，不是替人宣布通过。

## 07｜失败与重试

| 情形 | 处理 |
|---|---|
| 单阶段异常 | `state.json` 记 `error` + traceback 摘要，run 停在原阶段，下个 tick 重试；累计 3 次转 `blocked` |
| 网络失败（RSS/检索） | 记 warning，不阻塞本轮其他 run |
| 打回超过 3 次 | 转 `blocked`，等人工介入（说明是判据问题还是素材问题） |
| 同一 run 超过 7 天未推进 | 标记 `stale`，进日报提醒 |

**不自动重试的事**：涉及发布、删除、覆盖用户已确认版本的操作。

## 08｜产物与目录约定

沿用 v8 的命名，只加编排相关文件：

```
orchestrator/
├── loop.py                 # 入口：tick / submit / status / approve
├── state.py                # 状态机、持久化、非法转移校验
├── events.py               # inbox 扫描、RSS 扫描、去重
├── agents/                 # 九类智能体
├── providers/              # LLM 适配器（stub 为默认）
├── sources.json            # 源列表
├── inbox/                  # 手动投递
└── runs/{run_id}/
    ├── state.json          # 唯一真相
    └── events.log          # 追加式审计日志
```

案例产物仍写进 `NN_XX_案例/`，编排文件不进案例目录（避免污染交付物）。

## 09｜云端运行（GitHub Actions）

```yaml
on:
  schedule: [{cron: "0 */2 * * *"}]   # 每 2 小时
  workflow_dispatch:                   # 手动
  repository_dispatch: {types: [gzh-inbox]}  # 外部推送
```

一次 job = 一次 `tick`：

1. checkout 仓库（`gongzhonghao/`）
2. 恢复 `runs/` 缓存（或直接从仓库读）
3. `python3 orchestrator/loop.py tick --max-runs 3`
4. 产物与状态提交回仓库（`[loop] run xxx → drafted`）
5. 有 `awaiting_*` 或 `blocked` 时开/更新 Issue 提醒人

**为什么用 commit 回写而不是 artifact**：状态要能被人直接读、被 diff、被回滚；issue 里点一个标签就是审批。

**安全**：LLM key 存 Actions Secrets；只读源扫描不需要凭据；发布相关动作永远不自动执行。

## 10｜不变量（v9 不许破坏的事）

1. **v8 的所有内容规则原样有效**，v9 不得以"自动化"为由放宽任何一条。
2. **人物卡原样保护**：任何 agent 不得改写用户确认过的卡片 HTML。
3. **两轮分离**：内容优化与排版优化不合并；`composer` 改字即违规。
4. **人工闸门不可绕过**：`triaged` 与 `awaiting_publish` 必须有人参与，脚本不得提供 `--force-publish`。
5. **可追溯**：每个状态转移都写 `events.log`，含 agent 名、时间、产物哈希。
6. **失败要可见**：宁可停在 `blocked`，不许静默跳过。

## 与 v8 的关系一句话

v8 是**判据**，v9 是**执行**。判据进闸门，执行进循环；人只管两次点头——做不做，发不发。
